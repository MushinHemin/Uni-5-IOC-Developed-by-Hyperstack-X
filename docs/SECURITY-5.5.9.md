# Sonoma 5.5.9 — phase 2 security lifecycle

Local, uncommitted development baseline; not published. Scope: U03/U07/U08/U10/U28. Phase 1 tests and protocol remain in place. No database schema migration.

Successful login/register first clears the previous socket identity, all business-room subscriptions, typing timers, forum selection/list options and all tokens associated with the socket. Existing clients receive `loggedOut` before `authSuccess` on identity changes. Failed authentication does not silently change the current identity. Logout and disconnect use the same cleanup. Chat send, recall, typing and history validate current room access; room message/forum push recipients are checked against their current identity and selected resource.

Authentication revalidates the current user and the password hash captured when the socket authenticated. HTTP bearer tokens must still belong to the same authenticated live socket. Password reset commits the new hash first, then revokes every socket/token for that user and sends the existing `loggedOut` event. Persistence failure leaves the previous hash and sessions intact. New credentials can be used immediately. There is no new token TTL or durable reconnect session in this phase.

`ADMIN_PASSWORD` is now bootstrap-only. Existing administrator password/profile fields are never overwritten on startup, including when the environment contains an old password or no password. A missing administrator requires a non-placeholder bootstrap password of at least 12 characters; missing/weak configuration fails startup instead of creating a known-password administrator. The example configuration intentionally leaves this field empty. Keep `ADMIN_ACCOUNT` stable; changing it changes the configured administrator identity. Existing weak credentials are preserved, not silently rotated; the owner must decide and perform an authorized reset. The normal administrator password-reset action also rejects short/known placeholder passwords for an administrator.

The dashboard still exposes `{code,expiresAt}` and create-room still accepts `{name,code}`. Codes are six random decimal digits, valid for 10 minutes, used once after successful transactional room creation, and invalidated by restart. Failed database creation does not consume a code. A refreshed dashboard shows the next code after use. Non-admin attempts are limited to five per transport peer IP per ten minutes, with a bounded map. Forwarded headers are not trusted. Behind a reverse proxy, users share the proxy's quota; a separately reviewed trusted-proxy strategy may be needed. Codes are bearer invitations, not tied to a named recipient. Admin creation retains its existing bypass.

Tests use copied source, synthetic users and temporary SQLite. `npm test` runs both phases together. Production configuration, users, uploads and databases are not read for secrets or changed by this task. Known remaining issues include image cleanup, broader migration semantics, upload transport/voice MIME compatibility, dependency vulnerabilities and session reconnect/expiry design.
